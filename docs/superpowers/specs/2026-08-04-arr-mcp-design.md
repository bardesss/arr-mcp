# arr-mcp — Design

**Date:** 2026-08-04
**Status:** Approved
**Supersedes:** nothing (clean-room project)

## 1. Context

[`BerryKuipers/mcp_services_radarr_sonarr`](https://github.com/BerryKuipers/mcp_services_radarr_sonarr) is an MCP server exposing Radarr and Sonarr to AI assistants. It has 45 stars and 26 forks but was last pushed 2025-10-25, carries no license, and totals roughly 35 KB of Python. Its README concedes that watched/watchlist status "assumes these are tracked using specific mechanisms."

Demand is evident; the implementation is not worth inheriting. Two facts decide the approach:

- **No license means all rights reserved.** Publishing a derivative under our own name, or shipping images built from it, has no license grant behind it.
- **At 35 KB there is nothing meaningful to inherit.** The value is in which tools are worth exposing, which is not the copyrightable part.

**We build clean-room.** No upstream code is copied or consulted while writing.

**Amended 2026-08-04:** the README does *not* credit upstream. Nothing was copied, so there is nothing to attribute, and no licence obliges a mention. The README thanks the eight services and our dependencies instead. This section remains as the record of *why* the project is clean-room and MIT — that reasoning still governs §4's licence choice.

## 2. Goals

1. One MCP server covering the whole self-hosted media stack, not one per service.
2. Answer questions no single service can — cross-service correlation is the reason this exists.
3. Deploy as a single Docker container with a web config page that tests connections and shows logs.
4. Safe by default: destructive operations off until deliberately enabled.
5. A credible successor to the dead upstream: MIT, CI, multi-arch images, real tests.

## 3. Non-goals

- Not internet-exposed. LAN-only; no OAuth, no multi-user, no RBAC.
- Not a media player, requester UI, or replacement for any service's own web UI.
- Not a general MCP gateway. It knows about media services specifically.
- No Lidarr, Readarr, Plex, Tautulli, or qBittorrent in v1 (see §22).

## 5. Architecture

One container, one process. Splitting the MCP server from the config UI was considered and rejected: they share config state, cache and log store, so splitting means inventing IPC for a single-user homelab app.

```
┌─ arr-mcp container (Node 22 / TypeScript) ──────────────┐
│                                                          │
│  Hono HTTP server  :6060                                 │
│   ├─ /mcp        → MCP stateless HTTP, bearer-token auth │
│   ├─ /api/*      → config REST API (consumed by the UI)  │
│   ├─ /healthz    → liveness / readiness                  │
│   └─ /*          → React SPA, built into the image       │
│                                                          │
│  ── Core ──────────────────────────────────────────────  │
│   config       zod-validated YAML, hot-reloaded          │
│   resolver     cross-service identity join               │
│   cache        in-memory LRU + TTL, write-invalidated    │
│   logger       pino → stdout + SQLite ring buffer        │
│   audit        append-only write log (SQLite)            │
│   permissions  read / safe-write / destructive gate      │
│                                                          │
│  ── services/ (self-hosted, LAN) ──────────────────────  │
│   codegen:    Radarr Sonarr Prowlarr Jellyfin Seerr      │
│   handwritten: Bazarr SABnzbd Transmission               │
│                                                          │
│  ── providers/ (external, internet, optional) ─────────  │
│   IMDb dataset dump  (keyless; TMDB/OMDb deferred)       │
└──────────────────────────────────────────────────────────┘
         │                              │
   /config volume                LAN media services
  config.yaml + state.db
```

**Stack choices:**

- **Hono** — serves the MCP transport, config API and static SPA without ceremony; first-class TypeScript, small footprint.
- **`openapi-typescript` + `openapi-fetch`** — type-only generation, ~6 KB runtime, no generated client classes. Specs are vendored and regenerated by a script, so an upstream API change arrives as a reviewable diff rather than a runtime surprise.
- **`better-sqlite3`** — logs and audit. Logs and MCP call traces are capped as a ring buffer (30 days or 100 000 rows, whichever comes first) so `/config` cannot grow unbounded. **The write audit is exempt from trimming** — it is the record you need when something has gone wrong months later. No Redis, no Postgres.
- **Cache is in-memory.** Restart clears it. That is acceptable and removes a class of stale-state bugs.

**Protocol revision: 2026-07-28.** That revision made MCP stateless — no session initialization, no `Mcp-Session-Id`; each request carries protocol version, client identity and capabilities in `_meta`. The legacy HTTP+SSE transport is deprecated with a twelve-month offramp and **must not be adopted**. Roots, Sampling and Logging are deprecated but functional, and are not used.

This simplifies the design rather than complicating it: a single stateless process is trivially conformant, and the cache is already per-process rather than per-session. **No session state may be introduced into the transport layer** — that is the one way to get this wrong.

**Endpoint authentication.** `/mcp` requires a bearer token, generated on first run and shown in the config page. "LAN-only" is a network assumption, not a security control: the endpoint fronts eight API keys and, once enabled, file deletion, and a LAN contains guest phones and IoT devices. The `/api/*` config routes share the same token.

## 6. Adapters

Three of the eight services publish no usable OpenAPI spec: **Bazarr** (undocumented API), **SABnzbd** (query-parameter API), **Transmission** (RPC with an `X-Transmission-Session-Id` handshake).

**Therefore the adapter interface is defined by us and must be hand-writable.** Code generation is an implementation detail *inside* five adapters, never the shape of the contract. This is what keeps Transmission's session handshake from leaking into the design.

Every adapter implements:

```ts
interface ServiceAdapter {
  readonly id: ServiceId
  testConnection(): Promise<ConnectionDiagnosis>
  getVersion(): Promise<string>
  // capability-specific methods, narrowed per service
}
```

`testConnection` returns a **diagnosis, not a boolean** — see §14.

## 7. Metadata providers

A separate category from services, because the concerns differ: they live on the internet rather than the LAN, and their data changes slowly enough to cache for 24 h rather than minutes.

**v1 ships only keyless providers.** Keyed providers (TMDB, OMDb) are deferred to §22.

| Tier | Source | Provides | Cost |
|---|---|---|---|
| 0 | Radarr/Sonarr `ratings` + `/lookup`, Seerr discover | lookup without adding; ratings already held | free, no config |
| 1 | [IMDb dataset dump](https://datasets.imdbws.com/) | exhaustive, fast rating filters | nightly ~10 MB, no key |

Both stated use cases are covered without a key: "look up a movie without adding it" is `/api/v3/movie/lookup` on Radarr and `/series/lookup` on Sonarr, and "movies rated IMDb 8+" is a filter over the dataset join.

**Why the IMDb dump rather than OMDb for rating filters:** OMDb's free tier is 1 000 requests/day, one title per request. A 900-film library would consume the entire daily quota to answer a single question. `title.ratings.tsv.gz` refreshes daily, covers every title, needs no key, and joins locally on `imdbId`.

**A consequence worth stating: with only keyless providers, no information about the library ever leaves the network.** The IMDb dataset is a one-way bulk download — unlike a per-title API, it transmits nothing about what you own. Adding TMDB or OMDb later would change that, and the config page must say so at the point of entering a key rather than burying it in documentation.

The IMDb dataset is licensed for personal, non-commercial use. **We ship the fetcher; users fetch their own copy. The data is never redistributed.**

**TVDB is explicitly excluded.** Sonarr already sources its metadata from TVDB and exposes it through its own API. A direct TVDB client would duplicate a dependency Sonarr manages better.

## 8. Identity resolver

Shared core module, not tool-local — `get_library`, `get_media_details`, `diagnose` and `stack_health` all need the same join, and duplicating it is how joins drift apart.

Joins on `tmdbId` for movies and `tvdbId` for series, with `imdbId` as fallback. Radarr, Sonarr and Jellyfin (`ProviderIds`) all carry these.

Merged record:

```
{ title, year, ids,
  acquisition: { monitored, hasFile, quality, size },   ← Radarr/Sonarr
  playback:    { user, watched, playCount, lastPlayed },← Jellyfin, per-user (§9)
  ratings:     { imdb, tmdb, rottenTomatoes },          ← *arr + IMDb dump
  presence:    "both" | "arr_only" | "jellyfin_only" }
```

`presence` is diagnostically valuable: `arr_only` on an item with a file means a **broken Jellyfin import**; `jellyfin_only` means media nothing is managing. Neither is visible from any single service.

## 9. Multi-user identity

arr-mcp itself is single-user (§3). But two of the eight services have their own user concepts, and ignoring that leaves parts of the design undefined.

**Radarr, Sonarr, Prowlarr, Bazarr, SABnzbd and Transmission are single-tenant** — the API key is the entire authorization model and there are no users to distinguish. Nothing in this section applies to them.

**Jellyfin and Seerr are multi-user:**

- **Jellyfin** — watched state, resume position and favorites are *always* per-user; there is no global "watched". Library visibility can additionally be restricted per user.
- **Seerr** — every request belongs to a requesting user.

Two distinct needs follow, and one setting cannot serve both: scoping results to *you* ("only user X's library"), and reading *someone else's* state ("user Z's pending requests"). So:

**A configured default identity, plus an opt-in per-call override.**

```yaml
jellyfin:
  default_user: "Bartus"      # whose watched state `watched` means
  allow_other_users: false    # may tools query anyone else?
seerr:
  default_user: "bartus"
  allow_other_users: true     # required to read other users' requests
```

Both services issue admin-scoped API keys, so one key plus a user parameter can query as any user — that is the mechanism. `allow_other_users` exists to make that deliberate rather than incidental. When it is `false`, a tool call naming any other user is rejected with `AuthFailed` rather than silently falling back to the default.

**Consequences recorded honestly:**

- **An admin key means the model can read the whole household's viewing history and requests.** This is inherent to how Jellyfin and Seerr authorize and cannot be designed away here. `allow_other_users: false` is the default, and the config page states what enabling it exposes.
- **MCP is pull-based; there are no notifications.** Nothing in the protocol lets this server push. "Tell me about user Z's requests" is `get_requests(user: "Z", status: "pending")` when asked, or pending requests folded into the `weekly-report` prompt. A webhook receiver is deferred (§22) — and even with one, delivery still waits for the user to ask. The README must not imply otherwise.

## 10. Permission tiers

| Tier | Default | Contents |
|---|---|---|
| read | always on | all read tools |
| safe-write | on, per-service toggle | add, search, monitor, queue management, subtitle search |
| destructive | **off** | delete, raw request escape hatch |

Monitoring alone is safe-write; monitoring plus deletion is destructive. The model can pause and resume shows freely while file removal stays behind a switch you deliberately flip.

Every write tool accepts `dry_run: true`, returning what would change without changing it.

**Per-call confirmation for destructive operations.** Config toggles and `dry_run` are both set-and-forget: once the destructive tier is enabled, every delete runs unprompted forever. That is too weak for a tool that removes files, and it is the gap that untrusted content (§11) exploits.

The 2026-07-28 protocol provides **Multi Round-Trip Requests**. A destructive tool returns `resultType: "input_required"` describing exactly what it is about to remove; the client collects confirmation and re-issues the call with `inputResponses`. **The confirmation is produced by the server, so no tool argument and no phrasing by the model can skip it.**

Client support is not universal. **When the client does not advertise MRTR support, destructive tools are not exposed at all** — they do not silently degrade to unconfirmed execution. A user who genuinely wants unattended deletes sets `destructive.require_confirmation: false` explicitly, and the config page states what that removes.

## 11. Trust boundaries and untrusted content

**Everything a service returns is untrusted data, never instruction.** This is the security property most easily lost and the one no comparable project appears to address (§19).

The concrete threat: **Prowlarr returns release names from public indexers.** Those strings are attacker-controllable, and they flow straight into model context. Jellyfin overviews and provider metadata carry the same exposure. Tool responses reach the model with none of the scrutiny applied to user input, and a model may not distinguish passive data from directives. With destructive tools enabled, a crafted release name becomes an injection path into a system that deletes files.

Mitigations, in order of load-bearing-ness:

1. **Per-call confirmation for destructive operations (§10)** is the strongest control. A human sees the actual target before anything is deleted, so an injected instruction cannot complete a destructive action on its own.
2. **Free-text fields are fenced and labelled** — release names, overviews, file paths, and user-supplied notes are wrapped in an explicit data boundary in tool output, marked as untrusted content from a named service.
3. **Control characters and instruction-shaped sequences are stripped** from free-text fields before serialization.
4. **Tool output never influences authorization.** Permission tiers, `allow_other_users`, and confirmation requirements are decided from configuration alone. No value returned by a service can widen what the model may do.
5. **The write audit (§14) records the resolved target**, not the model's phrasing — so a delete is reviewable against what actually happened.

This does not make injection impossible. It makes the destructive path require a human, and makes everything else observable after the fact.

## 12. Tool surface

**20 tools, 18 exposed by default.** Tool count is a hard constraint, not a preference — model accuracy degrades measurably past roughly 40 tools, and eight services with per-endpoint tools would exceed 70.

### Read (13, always on)

| Tool | Spans | Notes |
|---|---|---|
| `search_media` | Radarr, Sonarr, Prowlarr, Jellyfin | `source: library \| discover \| indexers` |
| `get_library` | Radarr, Sonarr, Jellyfin | filters incl. year, genre, monitored, quality, **watched**, **rating**; `watched_by` (§9) |
| `get_media_details` | Radarr, Sonarr, Jellyfin | single item; episodes for series |
| `get_queue` | Sonarr, Radarr, SABnzbd, Transmission | unified queue |
| `get_calendar` | Radarr, Sonarr | upcoming and recently aired |
| `get_subtitles` | Bazarr | missing subs, languages, provider state |
| `get_playback` | Jellyfin | watch state, continue-watching, now playing; `user` (§9) |
| `get_indexers` | Prowlarr | health, grab stats, recent rejections |
| `stack_health` | all | versions, disk, failures, scan staleness |
| `diagnose` | all | **flagship** — causal chain for "why isn't X here?" |
| `lookup_media` | Radarr, Sonarr, Seerr | metadata lookup with no side effects |
| `discover_media` | Seerr | browse by genre/year/rating (Seerr's discover is TMDB-backed) |
| `get_requests` | Seerr | pending/approved/declined requests; `user` (§9) |

`get_library` spans Jellyfin because watched state exists only there — Radarr and Sonarr have no concept of it. This is the gap upstream never closed.

`watched_by` and `user` default to the configured `default_user` and are rejected for any other value unless `allow_other_users` is enabled (§9).

### Safe-write (5, on by default)

`add_media` · `search_release` · `set_monitored` · `manage_queue` (retry / remove without deleting) · `search_subtitles`

**`add_media` routes through Seerr when configured**, falling back to direct Radarr/Sonarr writes otherwise. The most common write action therefore lands in a human approval queue by default. This is the payoff for including Seerr.

Note: Overseerr and Jellyseerr merged into [**Seerr**](https://github.com/seerr-team/seerr) in February 2026; both originals sunset end of May 2026. One adapter, not two.

### Destructive (2, off by default)

**`delete_media`** — always deletes files. A delete that orphans files is a half-delete that then confuses every other tool in the stack, and surfaces as `jellyfin_only` in the library join.

```
delete_media(
  scope: "movie" | "series" | "season" | "episode",
  id, season_number?,
  unmonitor:     bool,  // default true — relevant to season/episode
  add_exclusion: bool,  // default true — relevant to movie/series
  dry_run:       bool,
)
```

`add_exclusion` guards a real trap: deleting something present on an import list causes it to return on the next sync. Radarr names this `addImportExclusion`, Sonarr `addImportListExclusion`; **the adapter normalizes the difference and the tool exposes one parameter.**

Season cleanup is `delete_media(scope: "season", …)` — unmonitors the season and deletes its files, so Sonarr will not re-grab. No separate tool.

**`service_request(service, method, path, body)`** — raw escape hatch covering every endpoint not wrapped above. Keeps the default surface small without making anything unreachable.

### Considered and rejected: Code Mode

[`dinglebear-ai/yarr`](https://github.com/dinglebear-ai/yarr) answers the same tool-count pressure differently: its default surface is a *single* tool that executes JavaScript in a sandbox against per-service callables. It is a legitimate design, and it is recorded here so it is not re-litigated later.

Rejected because it trades away the properties this spec is built on. A sandbox is a substantial component to maintain and secure. Permission tiers (§10) become porous once arbitrary code can compose calls. The write audit (§14) degrades from "deleted series 42" to "ran a script." And confirmation prompts must then reason about code rather than a resolved target, which is exactly what §11 needs to avoid.

`service_request` covers the same need — reaching something we did not wrap — with a fraction of the surface area, and it stays individually auditable and individually gated.

### Response shaping

Every read tool takes `detail: minimal | standard | full` (default `standard`) and a `limit` (default 50, hard maximum 500 regardless of what is requested).

Raw *arr responses are large; dumping a 900-film library into context exhausts it. Truncated responses **must** return `{ total, returned, truncated: true }` — silent truncation is how a model confidently reports that a 900-film library contains 50 films.

### Resources and prompts

Upstream exposed only tools. We also ship:

- **Resources:** `library://movies`, `library://series`, `queue://current`, `health://stack`
- **Prompts:** `diagnose-download`, `weekly-report`, `what-to-watch`, `subtitle-audit`

## 13. Configuration

`/config` volume, following the convention the rest of the stack already uses:

- `config.yaml` — services, API keys, permission toggles, provider settings. zod-validated, hot-reloaded.
- `state.db` — SQLite: logs, write audit, IMDb ratings table.

The web UI is the source of truth. Environment variables seed first-run defaults only.

```yaml
services:
  radarr:
    url: http://192.168.1.20:7878
    api_key: "…"
    permissions: { safe_write: true, destructive: false }
  jellyfin:
    url: http://192.168.1.20:8096
    api_key: "…"
    default_user: "Bartus"
    allow_other_users: false
  seerr:
    url: http://192.168.1.20:5055
    api_key: "…"
    default_user: "bartus"
    allow_other_users: true
providers:
  imdb_dataset: { enabled: true, refresh: daily }
```

## 14. Config page

**Dashboard landing** (approved layout B), **two-pane service detail** (layout C) behind each card.

- **Dashboard:** eight status tiles showing live health, latency and a per-service headline (`912 films`, `2 stalled`, `4 pending`). Broken services are impossible to miss. Log tabs sit below, always in view while testing.
- **Service detail:** URL and key fields, a Test button, the diagnosis, permission toggles, and that service's filtered log stream together on one pane.
- **Identity, for Jellyfin and Seerr only (§9):** a `default_user` picker populated from the service's own user list — typing a username by hand is a guaranteed source of silent mismatches — and an `allow_other_users` toggle. That toggle states what it exposes at the point of decision: *"Lets tools read any user's watch history and requests, not just Bartus."*

**Connection tests diagnose rather than pass/fail.** They distinguish DNS failure, connection refused, TLS error, 401 bad key, 404 wrong base path, and version-too-old, and state the remedy:

> 🔴 **Reachable, but rejected**
> TCP connect OK (6 ms) · HTTP 401 at `/api/system/status`
> → The API key is wrong. Bazarr → Settings → General.

**Three log streams, not one:** application log, MCP call trace, and **write audit**. The audit is separate and append-only because "what did the AI change, and when" is the record you actually want when something has gone wrong.

## 15. Error handling

Typed taxonomy across every adapter: `Unreachable`, `AuthFailed`, `NotFound`, `RateLimited`, `Timeout`, `VersionUnsupported`, `UpstreamError`.

Errors reach the model as structured, actionable text — `"Bazarr unreachable: connection refused at 192.168.1.20:6767"` — never a stack trace. A model told *why* something failed reports it; a model handed an opaque error invents an explanation.

**Cross-service tools degrade, they do not fail.** With Bazarr down, `diagnose` and `stack_health` return what they gathered plus `degraded: ["bazarr"]`. These two must work *especially* well when something is broken — that is their entire purpose.

Per-service timeout 10 s (configurable). Circuit breaker opens after 5 consecutive failures and half-opens for a single trial request after 60 s, so a dead service is not hammered. **Reads retry once on timeout; writes never auto-retry** — a retried `add_media` is a double-add.

## 16. Caching

In-memory LRU with per-entity TTL, invalidated on write. Library reads ~5 min, health ~30 s, provider metadata ~24 h, IMDb ratings table refreshed daily.

Beyond latency, this protects the media services from a model polling in a loop.

## 17. Testing, packaging, distribution

**Vitest**, with adapter tests against **recorded fixtures** — real API responses captured once and committed — so CI needs no live media stack.

- *Adapter tests* — request shaping and error mapping, per service
- *Contract tests* — assert vendored OpenAPI specs still match fixtures, catching upstream drift before users do
- *Tool tests* — output shape, plus **an assertion that each serialized response stays under a token budget**, making the shaping discipline in §12 mechanical rather than aspirational
- *Injection tests* — fixtures containing hostile release names and overviews, asserting that §11 fencing holds and that no tool output can alter a permission decision
- `diagnose` and the identity resolver get the heaviest coverage: most logic, least covered by types

No E2E against live services in CI; an optional local integration script exists for maintainers.

**Packaging:** MIT (we call HTTP APIs; no GPL code is linked). Multi-stage Dockerfile, non-root with PUID/PGID for the `/config` volume per linuxserver convention. GitHub Actions runs lint, typecheck and test on PR, and pushes multi-arch amd64/arm64 images to GHCR on tag. Renovate for dependencies.

**Distribution is a first-class deliverable, not an afterthought.** A survey of the field (§19) found fourteen comparable servers, essentially none with users — the *unmaintained* project this one succeeds still has the most stars of any of them. Discovery, not features, is the binding constraint. Phase 1 therefore ships a README that states the differentiator plainly, and the release checklist includes the MCP registry, Unraid Community Apps, Umbrel and CasaOS listings, and an r/selfhosted post.

```yaml
services:
  arr-mcp:
    image: ghcr.io/bardesss/arr-mcp:latest
    ports: ["6060:6060"]
    volumes: ["./config:/config"]
    environment: [PUID=1000, PGID=1000, TZ=Europe/Amsterdam]
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:6060/healthz"]
```

## 18. PR and release process

### The tool surface is the public API

The governing constraint. Renaming a tool or dropping a parameter breaks every user's saved prompts and agent configuration, and it breaks **silently** — the model stops finding the tool rather than raising an error. Tool-surface changes therefore get stricter treatment than a typical library's exports.

### Branching

Trunk-based. `main` is always releasable; short-lived branches; squash merge; linear history. The predecessor project defaulted to a long-lived `development` branch, which on a solo-maintained repo just creates a second place to forget to merge.

Branch protection on `main`: require status checks, require a PR, no direct pushes. **Approvals are not required** — a solo maintainer cannot approve their own PR, so that setting would block all merges permanently. CI is the gate.

### Checks on every PR

| Check | Purpose |
|---|---|
| lint + `tsc --noEmit` | fast fail |
| vitest — adapter, contract, tool, injection | §17 |
| `docker build`, no push | catches Dockerfile rot |
| token-budget assertions | enforces §12 mechanically |

**Plus a nightly job that does not run on PRs:** re-fetch the five vendored OpenAPI specs and, if any changed, open a PR containing the diff. This converts "Radarr shipped a breaking API change" from a user's bug report into a PR reviewed on a Tuesday. Roughly twenty lines, and the highest-value automation here.

### Release

**release-please.** Conventional Commits drive an always-open release PR that accumulates changes and maintains `CHANGELOG.md` and the version. Merging it tags and releases. Chosen over changesets, which suits monorepos and multi-contributor intent declaration — ceremony this project does not need.

```
PR merged to main  →  release-please updates its release PR
merge release PR   →  tag vX.Y.Z + GitHub Release
tag                →  buildx multi-arch → GHCR
                   →  SBOM + build provenance attestation
```

Provenance is ~5 lines via `actions/attest-build-provenance`. For an audience pulling this image onto a machine holding their media library, it is a credibility signal worth the effort.

**Image tags:** `X.Y.Z`, `X.Y`, `X`, `latest` for stable, plus `main` for bleeding edge. Nothing else.

### Versioning

**0.x until phase 6 ships, then 1.0.0.** The tool surface moves across phases 1–6, and 0.x permits that honestly rather than pretending otherwise.

After 1.0:

- Renaming or removing a tool, or removing a parameter → **major**
- Adding a tool or an optional parameter → minor
- **Deprecation policy:** a renamed tool retains its old name as an alias for one full minor, with the deprecation stated in the tool's description text — the one place the model will actually read it

### Contributor documentation

One document outranks the rest: **"how to add a service adapter."** The §22 deferred list — Lidarr, Readarr, Plex, Tautulli, qBittorrent — is precisely the work a contributor can complete in an evening, *provided* the adapter contract (§6) is documented and fixtures make it testable without owning the service. Done well, the deferred list clears itself.

The remainder is light: `CONTRIBUTING.md` covering local development against fixtures with no media stack required, and an issue template requesting service versions, arr-mcp version, and redacted logs.

## 19. Prior art

Surveyed 2026-08-04. Fourteen comparable MCP servers exist for this stack; none has meaningful adoption (0–9 stars each). The unmaintained project this one succeeds still leads the field at 45 stars, which is the clearest available evidence that **discovery, not capability, is the binding constraint** (§17).

| Project | Notes |
|---|---|
| [`dinglebear-ai/yarr`](https://github.com/dinglebear-ai/yarr) | Rust, MIT, the most sophisticated. Ten services, stdio + HTTP with bearer token, confirmation prompts on destructive dispatch, token-limit layer. Default surface is Code Mode (§12). **"The core server has no embedded UI."** |
| [`eejd/arr-controlarr`](https://github.com/eejd/arr-controlarr) | Advertises **"77 tools across 6 services"** — the precise anti-pattern §12 exists to avoid |
| `sandraschi/arr-mcp`, `clive-stokes/mediastack-mcp`, `CT4nk3r/arrstack-mcp`, and nine others | Varying subsets of the same services; mostly stdio, Python or TypeScript, no config UI |

**What the survey changed in this design:** endpoint authentication (§5), per-call destructive confirmation (§10), the untrusted-content section (§11), and treating distribution as a deliverable (§17).

**What it confirmed:** no comparable project ships a web config page, and none addresses untrusted tool content. Those are the differentiators — more than the tool surface.

## 20. Delivery phases

This design is too large for one implementation plan. It splits into six phases, each independently shippable and testable. Config is hand-written YAML until phase 5 — the UI edits a format that already works, rather than the format being invented to suit the UI.

| Phase | Delivers | Done when |
|---|---|---|
| 1 — Walking skeleton | Hono server, `/healthz`, stateless MCP transport at 2026-07-28, bearer auth, config loader, Radarr adapter, `stack_health`, Dockerfile, CI, README, **§18 repo setup** | A real MCP client calls `stack_health` against real Radarr, in Docker, green in CI; an unauthenticated request is rejected; merging a release PR publishes a tagged image |
| 2 — Services | Remaining 7 adapters, recorded fixtures, contract tests, all 11 non-correlating read tools, user identity binding (§9) | Every service reachable; read tools return shaped, budget-checked output; `allow_other_users: false` rejects other users |
| 3 — Correlation | Identity resolver, `get_library` three-way join, `diagnose` | `diagnose` returns a causal chain, and still works with a service down |
| 4 — Writes | Permission tiers, 5 safe-write tools, `dry_run`, write audit, 2 destructive tools, MRTR confirmation, §11 content fencing | Destructive off by default and unreachable without MRTR support; every write audited; no auto-retry; injection fixtures pass |
| 5 — Config UI | Dashboard, two-pane detail, diagnosing connection tests, three log streams | A service can be added and debugged without touching YAML |
| 6 — Providers | IMDb dump sync, `lookup_media`, `discover_media`, resources, prompts | Rating filters work; every tool degrades cleanly with the dump unsynced |

Phases 1–3 are the minimum that justifies the project's existence — a single server answering questions no individual service can. Phases 4–6 make it complete.

Phase 1 includes the §18 repository setup — branch protection, Conventional Commits, release-please, the nightly OpenAPI drift job, and provenance attestation. All of it is cheaper to establish before there is history than to retrofit onto it. The phases map to releases: 0.1 through 0.6, with **1.0.0 at the end of phase 6**, once the tool surface has stopped moving.

## 21. Verify during implementation

Open technical questions, each with a defined fallback. None blocks the design.

1. **Bazarr's API surface.** No public OpenAPI spec exists. Check whether a running instance exposes a generated swagger endpoint; if not, hand-write the adapter against the source.
2. **Radarr/Sonarr `ratings` field shape.** Radarr displays IMDb, TMDB and Rotten Tomatoes scores in its own UI, so the movie resource carries them, but the exact schema is unconfirmed (the API reference is a Swagger UI that does not scrape). Confirm against a live instance. Fallback: the IMDb dataset covers rating filters regardless.
3. **Seerr's OpenAPI spec path.** It carries Overseerr's spec forward; confirm the location.
4. **Per-user query parameters (§9).** Confirm how Jellyfin scopes item and playback queries by user with an admin API key, and whether Seerr's request endpoint filters by requesting user. Fallback if Seerr cannot filter server-side: fetch and filter in the adapter, which is acceptable at household request volumes.
5. **TypeScript SDK support for protocol revision 2026-07-28 (§5).** The revision is seven days old at time of writing; tier-1 SDKs were expected to ship support during the release-candidate window, but confirm before phase 1. **This is the one item that can affect the schedule** — if the SDK lags, phase 1 either pins the prior revision and migrates within the twelve-month offramp, or implements the transport directly. Decide once, at the start, not midway.
6. **MRTR client support in practice (§10).** Confirm how clients advertise Multi Round-Trip Request support and how a server detects its absence, since destructive tools are withheld when it is missing.

## 22. Deferred

**Keyed metadata providers.** v1 ships keyless providers only (§7). Add if the free tiers prove insufficient in practice:

- **TMDB** — discover by streaming provider, recommendations, similar titles. Free key. The gap versus Seerr's TMDB-backed discover is narrow, so this may never be needed.
- **OMDb** — Rotten Tomatoes, Metacritic, awards, box office. These scores exist nowhere else in the stack, but the 1 000/day per-title limit makes it viable only for on-demand single lookups, never bulk enrichment.

Adding either means library titles start leaving the network. The privacy note in §7 must be surfaced at the key-entry field when that happens.

**Services.** Lidarr and Readarr (near-free given a generic *arr adapter), Plex and Tautulli (genuinely different clients), qBittorrent, Trakt.

**Features.** Service auto-discovery via Prowlarr's existing app links or Docker labels.

**Seerr webhook receiver.** An endpoint accepting Seerr webhooks, surfacing recent events as an MCP resource. Note this does *not* create notifications — MCP has no push, so delivery still waits for the user to ask (§9). It only makes "what happened since I last looked?" answerable without polling Seerr.
